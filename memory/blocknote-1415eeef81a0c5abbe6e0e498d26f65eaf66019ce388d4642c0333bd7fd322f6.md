# 마우스 오른쪽 클립보드

아르곤 의견<br>삼성 DeX 전용으로 마우스 우클릭 호출을 구현하려면 안드로이드 입력 시스템의 제약과 DeX 사용성 충돌이라는 두 가지 전제를 먼저 해결해야 합니다. 안드로이드 접근성 서비스는 물리 키보드 입력(` onKeyEvent `)과 달리 다른 앱 위에서 발생하는 전역 마우스 우클릭(` MotionEvent.BUTTON_SECONDARY `)을 직접 가로채지 못하며, 만약 단일 우클릭 전체를 클립보드 호출로 덮어쓰면 브라우저·코드 에디터·파일 관리자의 기본 우클릭 컨텍스트 메뉴를 모두 잃게 됩니다.

**우클릭 트리거 구현 대안 3가지**

- **One UI 마우스 설정 연동:** 갤럭시 마우스 및 트랙패드 설정에서 보조 버튼(우클릭)을 앱 열기로 지정하고, UI 없이 서비스만 깨우는 투명 액티비티를 연결합니다. 구현이 가장 단순하며, 기본 우클릭 메뉴가 아쉬워지면 코드 수정 없이 휠 클릭이나 측면 버튼으로 매핑만 바꿀 수 있습니다.

- **Shizuku 기반 제스처 분리:** Shizuku(ADB 권한)로 마우스 원시 입력 이벤트를 감지해 단일 우클릭은 원래 DeX 컨텍스트 메뉴로 그대로 통과시키고, 더블 우클릭이나 길게 우클릭(약 0.35초)할 때만 팝업을 띄웁니다. 기존 DeX 조작감을 해치지 않으면서 어디서든 우클릭만으로 호출할 수 있는 가장 완성도 높은 방식입니다.

- **화면 가장자리 핫코너:** 추가 권한 없이 DeX 화면 상단이나 좌우 끝 4px 두께의 투명 접근성 오버레이를 띄워두고, 커서를 화면 끝에 대고 우클릭할 때만 ` MotionEvent.BUTTON_SECONDARY `를 감지해 팝업을 호출합니다.

**DeX 전용 설계 시 필수 처리 로직**

- **외부 모니터 디스플레이 분리:** 외부 모니터에 연결된 DeX는 휴대폰 본체(` Display.DEFAULT_DISPLAY `)와 별개의 디스플레이 ID에서 실행됩니다. 일반 컨텍스트로 오버레이를 생성하면 꺼져 있는 폰 화면에 팝업이 뜨므로, 현재 활성 윈도우의 ` displayId `를 추적해 해당 디스플레이 전용 컨텍스트 위에 창을 띄워야 합니다.

- **포커스 좌표 기반 컨텍스트 배치:** 대화면 모니터에서는 화면 정중앙에 창을 띄우면 마우스 이동 동선이 길어집니다. 팝업 호출 직전 포커스된 텍스트 입력창(` AccessibilityNodeInfo.FOCUS_INPUT `)의 화면 좌표를 읽어 입력창 바로 옆에 일반 우클릭 메뉴처럼 붙여서 렌더링하는 구조가 효율적입니다.

- **자동 붙여넣기 폴백(Fallback):** 항목을 좌클릭하거나 엔터를 칠 때 캐싱해 둔 이전 입력 노드에 ` AccessibilityNodeInfo.ACTION_PASTE `를 먼저 실행하되, 접근성 붙여넣기를 무시하는 웹 기반 에디터나 터미널 앱을 대비해 클립보드 교체 후 포커스 복원 및 붙여넣기 키 이벤트를 보내는 우회 경로를 함께 두어야 합니다.

기존 DeX 앱들의 기본 우클릭 메뉴를 살리는 방향(더블 우클릭·길게 우클릭 또는 휠·측면 버튼 활용)과 단일 우클릭 전체를 클립보드 전용으로 덮어쓰는 방향 중 어느 쪽으로 설계를 구체화할까요?

두 의견을 비교하니 흥미로운 차이가 있어.

- 제미나이(아르곤): 마우스 우클릭으로 클립보드를 호출하고, 선택한 내용을 어떻게 붙여넣을 것인가?

- ChatGPT: 클립보드 기록을 어떻게 안정적으로 수집·보관하고, 실제 작동하는 앱으로 만들 것인가?

둘은 경쟁하는 설계라기보다 사용자 인터페이스와 데이터 수집이라는 서로 다른 문제를 해결하는 설계에 가까워.

#### 1\. 설계 비교

| 항목 | 제미나이(아르곤) | ChatGPT |
| --- | --- | --- |
| 핵심 목표 | DeX 우클릭 클립보드 | Maccy형 기록 관리자 |
| 호출 방식 | 우클릭·더블 우클릭·핫코너 | 키보드 단축키 중심 |
| 팝업 위치 | 입력창 주변 | 작은 검색 팝업 |

내가 특히 좋게 평가하는 건 아르곤의 입력창 바로 옆에 팝업을 띄우자는 아이디어야.

DeX는 큰 모니터에서 사용하므로 팝업을 매번 중앙에 띄우는 것보다 입력 위치 주변에 띄우면 마우스 이동을 줄일 수 있어.

하지만 제안된 구현 방법들이 실제 안드로이드 시스템에서 가능한지는 별개 문제야.

#### 2\. 제미나이의 세 가지 우클릭 방법 검증

따라서 가장 간단한 구현이라고 단정하기 어려워.

기술 검증 필요

가장 흥미로운 아이디어야. 다만 Shizuku를 설치한다고 모든 시스템 입력 이벤트를 읽을 수 있는 건 아니야.

Android의 시스템 입력 감시 API에는 ` MONITOR_INPUT ` 권한 검사가 있으며, Shizuku도 ADB 권한의 한계를 그대로 받아. Git at Google +1

특히 단일 우클릭을 정상 전달하면서 더블 우클릭만 별도로 처리하는 동작은 구현 가능성을 아직 입증하지 못했어.

③ 화면 가장자리 핫코너

조건부 가능

셋 중 실험 대상으로 가장 현실적이야.

#### 3\. 제미나이가 더 잘 설계한 부분

실제 개발에 채택할 가치가 높은 아이디어는 두 가지야.

첫째, 외부 모니터의 디스플레이 ID를 구별하는 것.

DeX용 앱이라면 아주 중요한 고려사항이야. 안드로이드에는 특정 디스플레이를 위한 창 컨텍스트를 생성하는 API가 있으므로 구현 근거도 있어. [developer.android.com](<https://developer.android.com/>)

둘째, 접근성 ` ACTION_PASTE `를 이용하는 것.

이 역시 실제 Android API에 존재해. 따라서 자동 붙여넣기의 첫 번째 시도 방식으로 적합해. 다만 모든 입력창이 지원하는 것은 아니기 때문에 실패하면 수동 붙여넣기로 전환하는 구조가 필요해. [developer.android.com](<https://developer.android.com/>) +1

#### 4\. 그런데 두 설계 모두 해결해야 할 문제가 있어

바로 클립보드 기록 자체를 어떻게 수집하느냐는 거야.

Android 10 이후 일반 백그라운드 앱은 다른 앱의 클립보드를 자유롭게 읽을 수 없어. [developer.android.com](<https://developer.android.com/>)

이 문제를 해결하지 않으면 아무리 예쁜 우클릭 팝업을 구현해도 과거 복사 기록은 불완전할 수 있어.

따라서 두 설계의 우선순위를 합친다면 다음 구조가 좋겠어.

그러면 기록이 제한되는 상황에서도 직접 저장한 문장, 자주 쓰는 프롬프트, URL, 코드 조각을 우클릭으로 빠르게 불러오는 독립적인 도구가 될 수 있겠지.

37s 동안 처리함

ㅋㅋㅋ 다시 읽었어. 이번에 제미나이가 추가한 내용은 꽤 흥미로워. 특히 내가 지적했던 구현 불확실성을 일부 받아들이면서, 여러 호출 방식을 교체할 수 있는 구조로 발전시켰네.

그런데 네가 말한 것처럼 DeX 전용으로 가볍게 만든다면, 오히려 이번 설계를 좀 덜어내는 게 좋겠어.

#### 1\. 제미나이의 추가 제안

가장 중요한 변화는 이거야.

` TriggerSource `와 ` DexPopupController `의 분리

- ` TriggerSource `: 마우스나 키보드에서 호출 신호를 받음

- ` DexPopupController `: 클립보드 팝업을 표시함

- ` DataStore `: 사용자가 설정한 호출 방식을 기억함

이 구조는 괜찮아. 호출 방식을 바꿔도 클립보드 UI나 데이터 관리 코드를 다시 만들 필요가 없거든.

제미나이는 호출 모드도 네 가지로 확장했어.

| 호출 모드 | 내 판단 |
| --- | --- |
| One UI 버튼 연동 | 실제 지원 여부 미확인 |
| Shizuku 더블 우클릭 | 기술적 불확실성이 큼 |
| 화면 가장자리 우클릭 | 우선 실험할 가치 있음 |
| 키보드 단축키만 사용 | 가장 단순한 대안 |

다만 네 가지를 처음부터 모두 구현하는 건 경량 앱이라는 목표와 맞지 않아.

그리고 제미나이가 작성한 Kotlin 코드는 아직 설계 예시야. 문서에 있는 이벤트 처리 코드에는 일부 조건식과 식별자가 빠져 있어 그대로 실행할 수 있는 상태는 아니야.

#### 3\. 설계에서 한 가지 바꾸고 싶은 부분

제미나이는 마우스 클릭 감지에 많은 비중을 두고 있는데, 나는 팝업이 나타나는 위치와 호출 동작을 별도로 설계하고 싶어.

예를 들어 화면 오른쪽 가장자리에 작은 호출 영역을 두고, 그 영역을 우클릭하면 클립보드 메뉴가 열리는 방식이야.

일반적인 DeX 화면에서는 기존 우클릭 메뉴가 그대로 작동하고, 지정 영역에서만 우리 앱이 동작하게 하는 거지.

이렇게 하면 시스템 전체 마우스 이벤트를 가로챌 필요가 줄어들어. 물론 실제 오버레이가 외부 모니터에서 정상적으로 입력 이벤트를 받는지는 검증해야 해.

제미나이 :  
초기 실패 확률이 높은 요소(Shizuku, 자동 붙여넣기, 다중 설정)를 과감히 쳐내고 단일 APK로 핵심 동선부터 완성하자는 감량 방향은 매우 현실적이지만, '앱이 활성화됐을 때만 최근 클립보드를 읽어 저장한다'는 항목 하나에는 실제 사용성을 깨뜨리는 치명적인 빈틈이 있습니다.

- 우측 가장자리 핫존 단일화: 지정된 좁은 영역에서만 우클릭을 받으면 시스템 전역 마우스 이벤트를 가로챌 필요 없이 기존 DeX의 일반 우클릭 메뉴를 온전히 보존할 수 있습니다.

- 인터페이스 분리만 유지: 구현체는 가장자리 우클릭 하나만 만들되 TriggerSource와 팝업 컨트롤러의 경계만 남겨두면 코드 무게를 늘리지 않고도 추후 확장이 가능합니다.

반드시 짚어야 할 전제 오류: '활성화 시점 읽기'의 함정  
지피티 제안대로 백그라운드 기록을 빼고 팝업이 열릴 때만 클립보드를 읽으면, 작업 중 A 복사 → B 복사 → C 복사를 한 뒤 예전에 복사한 A를 꺼내려고 DexClip을 열었을 때 A와 B는 이미 유실된 상태가 됩니다. 정작 팝업을 여는 순간 저장되는 C는 이미 현재 클립보드에 들어 있어 굳이 앱을 열지 않고 바로 Ctrl + V를 누르면 되는 텍스트입니다.  
결국 백그라운드 수집을 완전히 빼면 '클립보드 히스토리(Maccy)'가 아니라 '자주 쓰는 프롬프트 보관함(스니펫 런처) + 수동 임시저장 도구'로 앱의 성격이 바뀝니다. 따라서 v0.1 착수 전에 아래 두 방향 중 실제 원하는 용도를 먼저 확정해야 합니다.

## 작업 지시: DexClip Diagnostic PoC v0.1 (Android Kotlin)

### 1\. 목적 및 범위

갤럭시 Fold5 + 삼성 DeX(외부 모니터) 환경에서 두 가지 핵심 가설(PoC A, PoC B)의 실사용 안정성을 검증하기 위한 **단일 진단용 네이티브 Android APK**를 작성하라.

- **포함:** 권한 설정 진입점, PoC A/B 개별 토글, 실시간 진단 로그 뷰(복사·초기화 버튼 포함)

- **제외 (엄격 적용):** 인터넷 권한, Room DB, Shizuku, 자동 붙여넣기(` ACTION_PASTE `), 클립보드 원문 저장, 복잡한 설정 화면

### 2\. 필수 아키텍처 원칙

기능은 최소화하되 향후 본 앱 확장을 위해 아래 두 인터페이스의 경계는 분리해 구현하라.

- ` TriggerSource `: 호출 입력(핫존 우클릭 등) 감지 및 콜백 전달

- ` DexPopupController `: 지정된 ` displayId ` 컨텍스트 위에 팝업 윈도우 표시·해제

### 3\. PoC A — DeX 외부 모니터 우측 핫존 우클릭

1. **외부 디스플레이 컨텍스트 생성:** ` DisplayManager `에서 기본 화면(` DEFAULT_DISPLAY `)이 아닌 활성 외부 모니터 ` Display `를 우선 탐색(없으면 기본 디스플레이 폴백)하고, ` createDisplayContext(display).createWindowContext(TYPE_APPLICATION_OVERLAY, null) `로 컨텍스트를 생성한다.

2. **비포커스 핫존 배치:** 외부 모니터 우측 가장자리 중앙부에 좁은 호출 오버레이(예: 폭 6\~8dp, 높이 160dp, 반투명 시각 표시 포함)를 ` FLAG_NOT_FOCUSABLE | FLAG_NOT_TOUCH_MODAL `로 띄워 일반 작업 창의 포커스나 기본 우클릭 메뉴를 방해하지 않게 한다.

3. **우클릭 감지 및 팝업 분리:** 핫존에서 마우스 우클릭(` MotionEvent.BUTTON_SECONDARY `)이 감지되면 ` DexPopupController `를 통해 동일한 외부 모니터 위에 포커스 가능한 작은 테스트 팝업(` TEST_A/B/C ` 감지 내역 표시, 바깥 클릭 및 ` ESC `로 닫힘)을 띄우고 로그를 기록한다.

### 4\. PoC B — 백그라운드 연속 복사(A→B→C) 및 순간 포커스 읽기

1. **이벤트 감지 (**` AccessibilityService `**):**

   - 물리 키보드 복사(` onKeyEvent `의 ` Ctrl+C `, ` Ctrl+Shift+C `): 원래 앱이 클립보드 쓰기를 먼저 마칠 수 있도록 반드시 ` ACTION_UP ` 감지 후 약 50ms 유예를 둔 뒤 포커스 획득을 요청한다(키 이벤트는 하위 앱으로 그대로 통과).

   - 마우스/시스템 복사 보조 감지: 윈도우 상태 변경이나 복사 관련 접근성 이벤트를 보조 트리거로 구분해 기록하되, 중복 읽기 디바운스를 둔다.

2. **이벤트 기반 순간 포커스 (1×1 투명 오버레이):**

   - 평상시 ` FLAG_NOT_FOCUSABLE ` 상태를 유지한다.

   - 복사 신호 수신 시 플래그에서 ` FLAG_NOT_FOCUSABLE `을 제거해 ` updateViewLayout `을 호출하고 요청 시각(` t0 `)을 기록한다.

   - 고정 슬립에 의존하지 말고 1×1 뷰의 ` onWindowFocusChanged(true) ` 콜백 시점에 즉시 ` ClipboardManager.getPrimaryClip() `을 읽은 뒤, 곧바로 ` FLAG_NOT_FOCUSABLE `로 원복한다.

3. **무응답 안전장치 (필수):**

   - 포커스 요청 후 **250\~300ms 이내**에 ` onWindowFocusChanged(true) `가 오지 않으면 타임아웃으로 판정하고 즉시 ` FLAG_NOT_FOCUSABLE `로 강제 복구해 DeX 키보드·마우스 입력 먹통을 방지한다.

### 5\. 진단 UI 및 테스트 통제 규칙

- **백그라운드 독립 동작:** UID 단위 포커스 판정 착시를 막기 위해 진단용 ` MainActivity `를 최소화(백그라운드 전환)하고 휴대폰 본체 화면을 끈 상태에서도 오버레이·접근성 서비스만으로 모든 실험이 정상 작동해야 한다(필요시 Foreground Service 유지).

- **원문 비노출 로그:** 클립보드 텍스트 원문은 절대 화면이나 로그에 출력하지 않는다. 읽은 문자열이 ` TEST_A `, ` TEST_B `, ` TEST_C ` 중 무엇과 일치하는지(그 외는 ` OTHER(len=N) `)만 판별해 아래 포맷으로 기록한다.

  - 기록 항목: ` [시각] [트리거 출처] [displayId] [포커스 획득 지연(ms)] [총 읽기 소요(ms)] [판별 결과: TEST_A | TEST_B | TEST_C | OTHER | NULL | TIMEOUT] `

- **화면 구성:**

  1. 권한 상태 배지 및 설정 바로가기 버튼 (` 다른 앱 위에 표시 `, ` 접근성 서비스 `)

  2. ` PoC A (DeX 우측 핫존) ` ON/OFF 스위치

  3. ` PoC B (백그라운드 자동 기록) ` ON/OFF 스위치

  4. 실시간 스크롤 진단 로그 창 + ` 로그 복사 ` / ` 로그 초기화 ` 버튼

### 6\. 요청 산출물

1. 바로 빌드 가능한 최소 Gradle 프로젝트 구조(` settings.gradle.kts `, ` app/build.gradle.kts `)

2. ` AndroidManifest.xml ` 및 ` res/xml/accessibility_service_config.xml ` (` flagRequestFilterKeyEvents ` 포함)

3. 전체 Kotlin 소스 코드 (누락·생략 없는 실행 가능 코드)

4. CLI 기준 디버그 APK 빌드 및 설치 명령어 요약
