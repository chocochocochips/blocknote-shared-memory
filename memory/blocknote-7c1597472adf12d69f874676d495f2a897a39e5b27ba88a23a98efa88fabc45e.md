# Sites Plus

## 하이브리드 AI 개발환경 구축 — 기획회의 1차

**프로젝트 가칭:** Hybrid AI Studio<br>**기획일:** 2026년 11월 17일<br>**현재 단계:** 아이디어 검토 및 아키텍처 설계

### 1\. 프로젝트 목표

ChatGPT Sites와 유사하게 자연어 채팅을 통해 웹앱을 제작하고, 실시간 목업을 테스트할 수 있는 개인용 AI 개발환경을 구축한다.

웹에서는 아이디어 검증과 프로토타이핑을 수행하고, 실제 소스 수정·빌드·배포가 필요할 때만 자체 Termux 또는 PC 개발환경을 연결하는 하이브리드 구조를 지향한다.

**핵심 원칙: 웹에서는 자유롭게 실험하고, 실제 환경에 반영할 때는 명시적으로 승인한다.**

### 2\. 개발환경 구성

#### A. 웹 기반 AI 개발 스튜디오

- AI 채팅을 통한 앱 제작 및 기능 변경

- 실시간 목업 생성과 브라우저 미리보기

- UI를 직접 조작하면서 기능 테스트

- 프로젝트별 대화·소스·수정 이력 관리

- 다양한 AI 모델을 선택할 수 있는 인터페이스

- 기존 실행 버전에 영향을 주지 않는 독립적인 실험 공간

#### B. 로컬 개발 실행환경

- Galaxy Fold5의 Termux 또는 별도 PC 개발환경 활용

- 웹에서 확정한 변경 사항을 로컬 프로젝트로 전달

- 실제 파일 수정, 패키지 설치, 빌드 및 테스트

- GitHub를 통한 버전 관리와 백업

- 수정 사항 검증 후 실제 서비스에 반영

- 실패 시 이전 안정 버전으로 복귀

Termux는 상시 가동 서버가 아니라 필요할 때 실행하는 개발 노드로 활용한다.

#### C. AI 모델 연결

이미 확보하거나 테스트한 AI 활용 경로를 최대한 재사용한다.

- Gemini API

- ModelScope 제공 모델

- Cloudflare Workers AI

- 기타 검증된 무료 AI API

- ChatGPT 구독 인증이 공식 지원되는 개발 도구(예: 지원되는 Codex 환경)

- 추후 로컬 LLM 연동

ChatGPT 구독 인증과 OpenAI API 과금은 구분한다. 구독 로그인으로 이용 가능한 개발 도구를 우선 검토하되, 일반 API 호출을 구독만으로 무료 사용할 수 있다고 가정하지 않는다.

목표는 특정 모델에 종속되지 않고 **작업에 따라 모델을 교체할 수 있는 개발환경**을 확보하는 것이다.

### 3\. 기본 작업 흐름

1. **기획:** 웹 채팅에서 AI와 요구사항 논의

2. **생성:** AI가 목업과 실행 가능한 프로토타입 제작

3. **검증:** 브라우저에서 직접 조작하며 수정 반복

4. **확정:** 검증된 버전을 개발 후보로 저장

5. **전달:** 로컬 Termux 또는 PC 개발환경 연결

6. **구현:** 실제 소스 수정·빌드·테스트

7. **반영:** 사용자 승인 후 적용, Git 버전 기록

웹 목업과 실제 배포 버전은 명확히 분리하고, 두 환경 사이의 변경 내용을 추적한다.

### 4\. 초기 기술 검토 후보

- [**bolt.diy**](<https://bolt.diy/>)**:** 브라우저 기반 AI 앱 빌더

- **Dyad:** 로컬 AI 앱 제작 및 미리보기

- **Codex CLI:** 실제 코드 수정과 테스트를 수행하는 에이전트

- **GitHub:** 소스 관리와 검증된 버전 저장

- **Termux:** 모바일 로컬 실행환경

- **미니PC:** 추후 상시 운영하는 개인 개발 서버 후보

기존 오픈소스를 최대한 활용하고, 필요한 연결 계층만 추가하는 방향으로 검토한다.

### 5\. 이번 기획회의의 핵심 쟁점

1. 웹 기반 개발 스튜디오를 어떤 오픈소스에서 출발할 것인가?

2. AI 채팅과 실시간 목업을 얼마나 통합할 수 있는가?

3. 기존 무료 API 및 ChatGPT 구독 인증을 어떤 방식으로 연결할 것인가?

4. 웹에서 확정한 소스와 실제 로컬 소스를 어떻게 동기화할 것인가?

5. Termux 실행·빌드 과정의 권한과 보안을 어떻게 통제할 것인가?

6. 실패 시 쉽게 복원할 수 있는 최소 개발 구조는 무엇인가?

### 6\. 1차 개발 범위

초기에는 완전한 개발 플랫폼을 만드는 것이 아니라 다음 세 가지 기능만 검증한다.

- 웹에서 AI와 대화해 간단한 앱을 생성한다.

- 생성한 앱을 실시간 미리보기에서 실행하고 수정한다.

- 확정된 소스를 로컬 개발환경으로 전달해 실제 실행한다.

**1차 성공 기준:** 하나의 간단한 앱을 웹에서 생성·검증한 뒤, Termux에서 실행하고 다시 웹 실험환경과 연결할 수 있을 것.

### 기획 방향

이번 프로젝트의 목적은 또 하나의 복잡한 개발 도구를 만드는 것이 아니다.

기존 ChatGPT Sites의 편리한 사용 경험은 유지하면서, AI 모델 선택권·소스 소유권·실행환경 통제권을 사용자에게 돌려주는 것이 핵심이다.

**AI는 교체할 수 있고, 실험은 실패할 수 있지만, 프로젝트와 개발환경은 지속되어야 한다.**

이 원칙을 바탕으로 오픈소스 조사, 최소 아키텍처 결정, 1차 PoC 구현 순으로 기획회의를 진행한다.

클로드 의견 :

문서 잘 읽었습니다. 요청하신 내용이 따로 없어서, 기획회의 1차 문서에 대한 검토 의견을 정리했습니다.

### 전체 평가

방향이 좋습니다. "웹은 실험, 로컬은 반영, 반영은 명시적 승인"이라는 원칙이 분명하고, 1차 범위도 세 가지로 좁게 잡았습니다. 특히 ChatGPT 구독 인증과 API 과금을 구분한 점은 나중에 가장 흔히 막히는 부분을 미리 막아 줍니다.

### 6개 쟁점에 대한 의견

**1\. 출발 오픈소스**<br>[bolt.diy](<https://bolt.diy/>)와 Dyad는 성격이 다릅니다. [bolt.diy](<https://bolt.diy/>)는 브라우저 안에서 앱을 생성하고 실행하는 방식이라 "웹 스튜디오" 쪽에 가깝고, Dyad는 로컬 데스크톱 앱이라 "하이브리드의 로컬 쪽"에 가깝습니다. 모바일 중심 작업이라면 [bolt.diy](<https://bolt.diy/>)를 출발점으로 두고 Dyad는 참고만 하는 쪽이 자연스럽습니다. 다만 두 프로젝트 모두 변화가 빨라서, 결정 전에 최신 릴리스, 라이선스, 지원 모델을 확인해야 합니다. 원하시면 제가 검색해서 비교해 드릴 수 있습니다.

**2\. 채팅과 목업의 통합**<br>처음부터 직접 만들지 말고, 오픈소스가 제공하는 기능을 그대로 쓰는 것이 좋습니다. 직접 구현할 부분은 모델 라우팅과 로컬로의 전달 계층 정도로 한정하는 편이 안전합니다.

**3\. 무료 API와 구독 인증**<br>모델을 교체 가능하게 하려면 앱과 모델 사이에 OpenAI 호환 엔드포인트 같은 얇은 공통 계층을 두는 것이 가장 중요합니다. Gemini, ModelScope, Workers AI는 이 계층 뒤에 두고, 구독 인증 기반 도구(Codex 등)는 앱에 끼우지 말고 "로컬 구현 단계의 에이전트"로 분리하세요. 구독 인증 토큰을 자체 웹앱에서 재사용하는 구조는 약관 문제로 막힐 수 있습니다.

**4\. 웹과 로컬 소스 동기화**<br>가장 단순하고 견고한 방법은 GitHub를 유일한 전달 경로로 쓰는 것입니다. 웹에서 확정하면 브랜치(예: ` candidate/… `)로 푸시하고, 로컬에서 pull해 작업한 뒤 승인된 것만 main에 병합합니다. 파일을 직접 주고받는 별도 채널은 만들지 않는 것을 권합니다. 추적, 백업, 롤백이 한 번에 해결됩니다.

**5\. Termux 권한과 보안**

- AI 에이전트는 지정한 프로젝트 디렉터리 안에서만 동작하게 합니다.

- 패키지 설치와 삭제, 외부 네트워크 접근, push는 매번 승인을 받습니다.

- API 키는 코드 저장소에 넣지 않고 환경변수나 별도 파일로 분리합니다.

- 읽기 전용 모드와 쓰기 모드를 구분해 시작합니다.

**6\. 복원 구조**<br>작업 전에 Git 태그나 커밋을 "안정 버전"으로 남기고, 실패하면 그 지점으로 되돌립니다. 최소 구조는 ` stable ` 브랜치와 ` candidate ` 브랜치 두 개면 충분합니다.

### 보완하면 좋을 점

- **1차 성공 기준에 실패 조건 추가:** 지금은 성공 조건만 있습니다. "3회 시도 내 실행 실패 시 중단" 같은 기준이 있으면 PoC가 끝없이 길어지지 않습니다.

- **PoC용 샘플 앱 미리 정하기:** 예를 들어 "메모 앱"처럼 아주 작은 앱 하나를 정해 두면 비교가 쉬워집니다.

- **모바일 환경 제약 확인:** 브라우저 미리보기와 Termux 빌드를 폰 하나에서 동시에 돌릴 때 메모리와 백그라운드 종료 문제가 생길 수 있어서, PoC 초기에 실측해 볼 가치가 있습니다.

다음 단계로 (1) [bolt.diy](<https://bolt.diy/>), Dyad, 그 외 후보의 최신 상태 조사, (2) 최소 아키텍처 다이어그램, (3) PoC 체크리스트 중 어느 것부터 진행할까요?<br><br><br>Hybrid AI Studio 기획안 (참여자 제안 v0.1)

기존 문서의 원칙은 그대로 두고, 제가 보기에 설계가 달라져야 하는 부분을 중심으로 작성했습니다.

### 0\. 핵심 제안: 스튜디오보다 인계 규격을 먼저

문서는 웹 스튜디오를 어떤 오픈소스로 만들지에 무게를 두고 있습니다. 저는 이 프로젝트의 성패가 **웹에서 만든 결과를 로컬이 믿고 받을 수 있는 규격**에 달려 있다고 봅니다. 스튜디오는 bolt.diy 같은 기존 도구로 교체할 수 있지만, 인계 규격이 없으면 웹과 로컬이 계속 어긋납니다. 그래서 이 규격을 **Candidate Package**라는 단위로 정의하고 그것을 중심에 놓겠습니다.

### 1\. 3계층 + 1게이트 구조

| 계층 | 역할 | 성격 |
| --- | --- | --- |
| **Studio** (웹) | 대화, 목업, 미리보기 | 버려도 되는 실험 공간 |
| **Bridge** (GitHub) | 후보 전달, 이력, 승인 | 유일한 전달 경로 |
| **Workshop** (Termux/PC) | 실제 수정·빌드·테스트 | 정본(source of truth) |
| **Model Gateway** | 모델 라우팅 | 위 세 계층과 독립 |

**Termux는 상시 가동이 아니므로 "웹이 로컬로 보내는" 푸시 방식은 맞지 않습니다.** GitHub에 후보를 올려 두면 로컬이 켜졌을 때 가져가는(pull) 비동기 구조가 훨씬 안정적입니다.

### 2\. Candidate Package 규격

웹에서 "확정"을 누르면 ` candidate/<id> ` 브랜치에 아래 내용이 올라갑니다.

- 소스 코드 전체

- ` SPEC.md `: 요구사항과 결정 사항 요약

- ` PROMPT_LOG.md `: 어떤 지시로 만들었는지

- ` manifest.json `: 생성 모델과 시각, 의존성 목록, 미리보기에서 확인한 항목, 알려진 문제

로컬 AI는 코드만이 아니라 이 패키지 전체를 읽고 시작합니다. 대화 맥락이 파일로 넘어가므로, 모델이 바뀌어도 프로젝트가 이어집니다.

### 3\. 승인 게이트

- Workshop의 에이전트는 ` work/<id> ` 브랜치에서만 작업합니다.

- ` main ` 병합은 **사용자가 직접 PR을 승인**할 때만 가능합니다. 이것이 문서의 "명시적 승인"을 구현하는 방법입니다.

- 권한은 4단계로 나눕니다.

  - **T0:** 읽기

  - **T1:** 프로젝트 폴더 안에서 쓰기

  - **T2:** 패키지 설치, 외부 네트워크 접근 (매번 승인)

  - **T3:** push, 배포 (diff 확인 후 승인)

### 4\. Model Gateway

- 앱과 도구는 OpenAI 호환 엔드포인트 하나만 바라봅니다.

- 라우팅 설정은 파일 하나로 관리합니다. 예: 기획은 모델 A, 코드 생성은 모델 B, 장애 시 무료 모델로 대체.

- Cloudflare Worker로 게이트웨이를 두면 API 키가 브라우저에 노출되지 않습니다.

- **구독 인증 기반 도구(Codex CLI 등)는 게이트웨이에 넣지 않고 Workshop의 에이전트 역할로만 씁니다.** 구독 인증을 자체 앱에 재사용하는 구조는 약관 위반 소지가 있기 때문입니다.

### 5\. 복원 구조

- 반영 직전에 ` stable-YYYYMMDD ` 태그를 남깁니다.

- 배포는 "새 버전 복사 후 전환" 방식으로 해서, 이전 버전으로 되돌리는 데 명령 한 번이면 되게 합니다.

- 웹 Studio는 어떤 경우에도 실행 중인 서비스에 접근하지 못합니다.

### 6\. 단계별 계획과 판정 기준

**P0. 도구 비교 (1\~2일)**<br>같은 샘플 앱(예: 단일 화면 메모앱)을 후보 2\~3개로 만들어 비교합니다. 이 단계에서는 코드를 새로 만들지 않습니다.

- 통과: 5턴 안에 동작하는 미리보기 확보

- 이때 **폰 브라우저에서 실제로 되는지**가 가장 중요한 판정 항목입니다.

**P1. 인계 PoC**<br>Candidate Package를 수동으로 만들어 GitHub에 올리고, Termux에서 pull해 실행합니다.

- 통과: 인계부터 로컬 실행까지 10분 이내, 이전 버전 복원 1분 이내

**P2. 게이트웨이**<br>모델 2개 이상을 설정 파일 변경만으로 교체합니다.

**P3. 권한 통제 강화**<br>T0\~T3 단계를 에이전트 실행 환경에 실제로 적용합니다.

### 2\. Candidate Package v0.1 최소 규격 (1페이지)

#### 2.1 원칙

1. 후보는 **하나의 커밋 SHA**를 가리키며, 확정 후 수정하지 않습니다. 수정은 새 후보로 만듭니다.

2. 인계 정보는 코드 옆의 파일로 둡니다. 대화 속에만 있는 맥락은 없는 것으로 봅니다.

3. 비밀 값(API 키, 개인정보)은 어떤 파일에도 넣지 않습니다.

#### 2.2 필수 파일 (` /handoff/ ` 디렉터리)

| 파일 | 내용 |
| --- | --- |
| ` manifest.json ` | 아래 필드 |
| ` SPEC.md ` | 요구사항, 확정한 결정, 제외한 것 (사람이 확인) |
| ` KNOWN_ISSUES.md ` | 알려진 문제, 미검증 항목 |
| lockfile | 의존성 고정 (예: package-lock.json) |
| ` PROMPT_SUMMARY.md ` | 핵심 지시와 수정 요약 (원문은 선택) |

#### 2.3 manifest.json 필드

```json
{
  "schema": "candidate/0.1",
  "candidate_id": "memo-001-c1",
  "project_id": "memo-app",
  "base_commit": "<main의 기준 커밋 SHA>",
  "candidate_commit": "<후보 커밋 SHA>",
  "created_at": "2026-11-17T00:00:00+09:00",
  "created_by": { "tool": "<웹 빌더 이름·버전>", "model": "<모델명>" },
  "export_method": "manual-zip | git-push",
  "preview_checks": [
    { "item": "항목 설명", "result": "pass | fail | untested" }
  ],
  "run_commands": { "install": "", "start": "", "test": "" },
  "secrets_required": ["ENV_VAR_NAME"]
}
```

` secrets_required `에는 값이 아니라 **이름만** 적습니다.

#### 2.4 상태 전이

```text
DRAFT → CANDIDATE → VERIFIED → APPROVED → DEPLOYED
                 ↘ REJECTED (어느 단계에서든)
```

| 전이 | 누가 | 조건 |
| --- | --- | --- |
| DRAFT → CANDIDATE | 사용자 (Studio에서 확정) | 후보 커밋 생성, handoff 필수 파일 완비 |
| CANDIDATE → VERIFIED | Workshop | pull 후 install/start/test 통과, 결과를 ` STATUS.md `에 기록 |
| VERIFIED → APPROVED | **사용자만** | PR 승인과 main 병합 (에이전트는 불가) |
| APPROVED → DEPLOYED | 사용자 (수동 실행) | 배포 직전 ` stable-YYYYMMDD ` 태그 생성 |
| → REJECTED | 사용자 또는 Workshop | 사유를 ` STATUS.md `에 기록, 후보는 삭제하지 않고 보존 |

상태 기록은 ` STATUS.md `에 **추가만 가능**한 로그로 남기며(시각, 주체, 전이, 근거), ` manifest.json `은 고치지 않습니다. 이렇게 하면 불변성과 이력이 함께 유지됩니다.

#### 2.5 인계 거부 조건 (Workshop이 패키지를 받지 않는 경우)

- 필수 파일 누락 또는 lockfile 없음

- ` candidate_commit `이 저장소에 존재하지 않음

- 소스에 비밀 값으로 보이는 문자열이 포함됨

### 3\. P0 최우선 검증: export 완전성

모바일 미리보기보다 **export가 실제 소스를 누락 없이 내보내는가**를 먼저 봅니다. 미리보기만 되고 소스를 못 꺼내면 이 구조 전체가 성립하지 않기 때문입니다.

- [ ] export한 소스를 빈 디렉터리에서 install, start만으로 실행할 수 있는가

- [ ] 미리보기에서 보이는 모든 기능이 export본에도 있는가

- [ ] 웹 빌더가 내부 전용 파일이나 숨은 의존성을 요구하지 않는가

- [ ] lockfile이 포함되는가

- [ ] export 결과에 비밀 값이 섞이지 않는가

- [ ] 두 번 export했을 때 결과가 같은가 (재현성)

- [ ] 위 과정이 폰과 DeX 중 실제 사용할 환경에서 되는가

**실패 시 대안:** export가 불완전하면 Studio에서는 목업만 만들고, 실제 소스는 Workshop 쪽 에이전트가 목업을 보고 새로 구현하는 구조로 바꿉니다. 이 경우 Candidate Package의 중심이 코드에서 ` SPEC.md `로 옮겨 갑니다.

- Codex CLI 구독 인증의 적용 범위와 Termux 호환성: OpenAI Codex CLI는 ChatGPT 플랜 기반 Codex 인증 안내에 따라 Plus·Pro 계정 OAuth 로그인(헤드리스 환경용 codex login --device-auth 포함)을 공식 지원합니다. 다만 이 인증 세션은 공식 Codex CLI·IDE 내부 전용이므로 웹 스튜디오([bolt.diy](<https://bolt.diy/>) 등)의 일반 API 프로바이더로 빼내어 재사용할 수는 없습니다. 또한 공식 패키지의 Linux ARM64 바이너리는 musl 기반으로 빌드되어 순수 Android Termux(Bionic libc)에서는 바로 실행되지 않으므로(Codex Termux 호환성 이슈 \#2951), Termux 내부의 proot-distro Ubuntu(ARM64) 환경에서 구동하거나 별도 네이티브 빌드(codex-termux)를 활용해야 합니다.

### 2\. 설계 문제 2건: 수정안

#### 문제 1. 커밋 SHA 자기참조

manifest.json에 자기 커밋 SHA를 적을 수는 없습니다. 파일을 수정하는 순간 SHA가 바뀌기 때문입니다.

**수정:**

- ` manifest.json `에는 ` base_commit `**만** 남깁니다. 후보 커밋 SHA는 파일 안에 넣지 않습니다.

- 후보의 정체는 **보호된 태그** ` candidate/<id> `**가 가리키는 커밋**으로 정의합니다. 태그는 커밋 내용의 일부가 아니므로 자기참조가 없고, 태그 보호로 이동과 삭제를 막을 수 있습니다.

- 후보 커밋 SHA는 아래 인계 기록(ledger)에 함께 적어, 태그가 실수로 바뀌어도 대조할 수 있게 합니다.

#### 문제 2. 불변 후보와 STATUS.md 충돌

후보 커밋 안의 ` STATUS.md `를 계속 고치면 불변 원칙이 깨집니다.

**수정:** 상태 이력은 후보 커밋 **밖**으로 옮깁니다.

- 후보마다 **PR 하나**를 만들고, 상태 전이는 라벨과 댓글로 남깁니다. 검증 댓글에는 반드시 **검증한 커밋 SHA**를 적습니다.

- PR 도구가 번거로운 1차 수동 PoC에서는 ` ledger ` 전용 브랜치에 **추가만 하는 기록 파일 하나**(한 줄이 한 사건)를 둡니다. 각 줄은 ` 시각, 주체, 후보 id, 후보 SHA, 전이, 근거 `를 담습니다.

- 후보 소스가 바뀌면 새 후보(` -c2 `)가 됩니다. 이미 VERIFIED였던 후보의 SHA가 바뀌었다면 VERIFIED는 무효이고 CANDIDATE로 되돌립니다.

#### 수정된 manifest 필드 (변경점)

```json
{
  "schema": "candidate/0.2",
  "candidate_id": "todo-001-c1",
  "project_id": "todo-app",
  "base_commit": "<기준 커밋 SHA>",
  "created_at": "...",
  "created_by": { "tool": "", "model": "" },
  "export_method": "manual-zip | git-push",
  "preview_checks": [],
  "run_commands": { "install": "", "start": "", "test": "" },
  "secrets_required": []
}
```

` candidate_commit ` 필드를 제거하고, 후보 식별은 태그와 ledger가 맡습니다. 필수 파일에서도 ` STATUS.md `를 빼고 ` handoff/ ` 안에는 ` manifest.json `, ` SPEC.md `, ` KNOWN_ISSUES.md `, ` PROMPT_SUMMARY.md `, lockfile만 둡니다.

**인계 거부 조건 추가:** 후보 태그가 가리키는 커밋이 ledger의 SHA와 다르면 Workshop은 받지 않습니다.

**버전 기록:** v0.1 (2026-11-17, Claude 초안) → v0.2 (후보 SHA 자기참조 제거, 상태 기록을 후보 밖으로 분리, 태그 보호·ledger 표현 정정). 상태: 조건부 채택, 실행 검증 전.

**1\. 원칙**

1. 후보는 Git 커밋 하나로 고정하며, 확정 후 소스를 수정하지 않는다. 수정은 새 후보(` -c2 `)로 만든다.

2. 인계 정보는 코드 옆 파일로 둔다. 대화 안에만 있는 맥락은 없는 것으로 본다.

3. 비밀 값은 어떤 파일에도 넣지 않는다. ` secrets_required `에는 변수 이름만 적는다.

4. 상태 이력은 후보 커밋 밖에 둔다.

**2\. 후보 식별**

- 후보 = 보호 태그 ` candidate/<id> `가 가리키는 커밋. manifest에는 자기 SHA를 쓰지 않는다 (` base_commit `만 기록).

- 후보 SHA는 인계 기록(ledger 또는 PR)에 함께 적는다.

- 태그 보호는 이름만으로 되지 않으므로, 생성·수정·삭제를 제한하는 **Ruleset 적용을 실제로 시험해 확인**한다. 확인 전에는 "보호됨"이라고 쓰지 않는다.

**3\.** ` handoff/ ` **필수 파일**<br>` manifest.json `, ` SPEC.md `(사람이 확인한 결정 사항), ` KNOWN_ISSUES.md `, ` PROMPT_SUMMARY.md `(원문은 선택), lockfile

**4\. manifest.json (v0.2)**<br>` schema `, ` candidate_id `, ` project_id `, ` base_commit `, ` created_at `, ` created_by{tool, model} `, ` export_method `, ` preview_checks[] `, ` run_commands{install, start, test} `, ` secrets_required[] `

**5\. 상태 전이와 승인**

| 전이 | 주체 | 근거 |
| --- | --- | --- |
| DRAFT → CANDIDATE | 사용자 | 후보 태그 생성, 필수 파일 완비 |
| CANDIDATE → VERIFIED | Workshop | 해당 SHA를 checkout해 install, start, test 통과, 검증 SHA 기록 |
| VERIFIED → APPROVED | 사용자만 | main 병합 승인 (로컬 테스트 승인과 별개) |
| APPROVED → DEPLOYED | 사용자 | 배포 전 ` stable-YYYYMMDD ` 태그, 배포 후 동작 확인 |
| → REJECTED | 사용자·Workshop | 사유 기록, 후보는 삭제하지 않음 |

- 후보 SHA가 바뀌면 이전 VERIFIED는 무효이며 새 후보가 된다.

- 검증 SHA와 병합·배포 SHA는 **별도로 기록**한다. 병합 방식에 따라 달라질 수 있기 때문이다.

**6\. 상태 기록 (ledger)**<br>1차 PoC는 ` ledger ` 브랜치의 추가형 기록 파일 하나를 쓰고, 이후 PR 라벨·댓글로 옮길 수 있다. 한 줄에 ` 시각, 주체, 후보 id, 후보 SHA, 전이, 근거 `를 적는다. force-push 금지와 쓰기 권한 제한을 적용한다. 완전한 불변 감사 로그를 보장하지는 않는다.

**7\. 인계 거부 조건 (Workshop)**<br>필수 파일 또는 lockfile 누락 / 태그가 가리키는 SHA와 ledger의 SHA 불일치 / 소스에 비밀 값으로 보이는 문자열 포함

**8\. 롤백**<br>worktree 제거는 작업 격리 해제일 뿐 운영 롤백이 아니다. 배포 버전, 데이터 마이그레이션, 서비스 전환과 복귀는 별도로 검증한다.

**9\. 이번 단계에서 하지 않는 것**<br>설치, API 키 등록, GitHub 토큰 권한 변경, 새 저장소 생성, 본문 변경
