# 엑사원 연동 방향

\# K-EXAONE 2.5 API × BlockNote Lab 연동 검토  
작성 기준: 2026-11-13 대화 내용. 실제 연동 전 공식 문서와 약관을 재확인할 것.

\#\# 1. 검토 목적  
BlockNote Lab에 K-EXAONE 2.5를 Gemini, Qwen과 나란히 연결하여 한국어 문서 검토 및 포스트잇 피드백 모델로 사용한다. 기존 문서의 소유권·승인 원칙을 유지한다. AI가 본문을 자동으로 고치지 않고, 검토 결과를 포스트잇 보관함에 남기도록 시작한다.

\#\# 2. 공개 API 관련 파악 사항  
\- 제공 주체: LG AI연구원 / EXAONE API  
\- 대화에서 확인한 공개 시점: 2026-11-09  
\- API: OpenAI 호환 Chat Completions  
\- Base URL: https://api.exaone.ai/v1  
\- Model ID: k-exaone\_v2.5  
\- 모델 특성: 한국어 중심, 코드 작성·도구 활용 가능성, 추론 강도 선택(low / high / max)  
\- 발표된 모델 규모: 전체 750B, 활성 31B 파라미터; 컨텍스트 최대 약 524,288토큰  
\- 호스팅 추론 방식이므로 폴드5 DeX에 모델 자체 설치는 필요 없음  
\- API 키 유효기간 30일이라는 안내와 무료 호출 기본 100회/일이라는 안내가 있었으나, 실제 계정·정책 화면에서 재확인 필요  
\- 무료 API의 제공 종료일은 확정되지 않았으므로 장기 무료 운영을 전제로 설계하지 말 것

\#\# 3. 권장 구현 구조  
BlockNote Lab(문서·채팅·포스트잇)  
→ 서버 측 프록시(예: Cloudflare Worker, API 키 비밀값 보관)  
→ Gemini / Qwen / K-EXAONE 2.5

\- 기존 두 모델의 코드를 수정·대체하지 말고 EXAONE을 별도 선택지로 추가한다.  
\- OpenAI 호환 API 클라이언트를 재사용할 수 있는지 확인한다.  
\- EXAONE 응답에서 reasoning\_content(추론 내용)와 content(최종 답변)가 분리될 수 있으므로 표시·파싱 검증.  
\- 기본 추론 강도는 low, 문서 검토가 까다로운 경우에만 high로 시험.  
\- 마지막 요청의 성공/실패, 사용 모델, 호출 시각 등을 기존 표시 기능과 동일한 방식으로 노출.  
\- API 키를 공개 프런트엔드 JavaScript 또는 GitHub 저장소에 포함하지 않는다.

\#\# 4. 약관 및 운영상 주의  
\- 무료 제공과 상업적 사용 허가는 별개다.

\- 우선 개인·비상업적 테스트 범위로 실험하고, 공개 사이트에서 다중 사용자를 위한 호출 기능을 제공하기 전 약관을 다시 확인한다.  
\- 모델 성능 홍보 자료를 그대로 신뢰하지 말고 한국어 문서 검토, 도구 호출, 저장 형식의 실제 결과로 판단한다.

\# K-EXAONE 2.5의 에이전트 활용 방안 — BlockNote Lab

작성: ChatGPT / 2026-11-13  
성격: 기존 문서에 대한 추가 검토 의견. 자동 구현이나 본문 변경 지시가 아닌 검증용 제안.

\#\# 1. 핵심 결론  
EXAONE을 단순 응답형 모델이 아니라 도구를 선택하고 작업 흐름을 판단하는 '에이전트의 추론 엔진'으로 활용할 수 있다. 다만 EXAONE 모델 자체가 문서나 파일을 직접 수정하는 것은 아니다. 모델의 도구 호출 결과를 처리하는 별도 실행기와 BlockNote MCP 도구가 있어야 한다.

활용 방향은 두 가지:  
\- 문서 에이전트: 문서·포스트잇 조회, 이력 비교, 모순 및 구현 위험 분석, 검토 결과 포스트잇 저장.  
\- 개발 에이전트: 소스코드 탐색, 수정안 작성, 테스트·오류 분석. 실제 쓰기·실행 권한은 분리하여 통제.

\#\# 2. 외부 에이전트 실행기 후보  
\- Hermes Agent: 범용 작업 계획·도구 호출 중심. 문서 관리 에이전트 실험 후보.  
\- OpenCode: 개발·코드 검증 중심. BlockNote Lab 프로젝트 코드 분석과 테스트에 적합.  
\- EXAONE 공식 개발 자료에는 에이전트 연결 가이드 및 도구 호출 관련 안내가 있는 것으로 확인했으나, 특정 버전·기능·설정은 구현 전 최신 공식 문서 기준으로 검증할 것.  
\- OpenCode와 EXAONE API, BlockNote MCP를 연결하는 개인용 최소 실험을 우선 고려.

\#\# 3. 제안 아키텍처  
사용자 요청  
→ EXAONE 2.5 (추론·계획·도구 선택)  
→ 에이전트 실행기 (도구 호출·응답 재전달·반복 제어)  
→ BlockNote MCP (인증·권한·실제 기능 실행)  
→ 문서 조회 / 이력 조회 / 포스트잇 조회 / 포스트잇 저장  
→ EXAONE 결과 확인  
→ 필요시 다음 도구 호출 또는 최종 응답

현재 BlockNote 커넥터에서 확인 가능한 실제 도구 예:  
\- list\_documents: 문서 목록 조회  
\- read\_document: 블록·본문·revision 조회  
\- read\_document\_history: 수정 이력 조회  
\- list\_postits / read\_postit: 기존 코멘트 조회  
\- save\_postit: 보관함에 의견 남기기  
\- insert\_postit / apply\_paragraph\_edits: 문서 변경 가능하므로 사용자 명시적 승인 단계에서만 제한적 허용

중요: 현재 BlockNote MCP 기능이 존재한다고 해서 EXAONE과 외부 에이전트 실행기 사이의 연동이 이미 완료된 것은 아니다. 엔드포인트 연결·인증·스키마 호환성·오류처리는 별도 실측 필요.

\#\# 4. 대표 활용 시나리오  
사용자 요청: "엑사원 연동 방향 문서를 읽고, 구현상의 위험과 공식 문서에 맞지 않는 부분을 점검해 줘. 이전 포스트잇과 중복되는 의견을 피하고 새로운 내용만 포스트잇에 저장해."

에이전트 예상 작업:

1) 문서 목록에서 목표 문서 확인
2) 본문 및 revision 읽기
3) 기존 포스트잇 목록·주요 의견 확인
4) 기술·약관·구현 가정 검증, 중복 제거
5) 출처·불확실성 표시한 피드백 생성
6) save\_postit 호출
7) 저장 성공 결과 확인 후 사용자에게 알림

본문 수정은 승인 전 금지. 사용자 승인 후 보관된 의견을 insert\_postit으로 삽입하는 기존 방식을 유지한다.

\#\# 5. 추천 구현 순서  
1단계(낮은 난도): EXAONE API로 OpenCode 독립 실행 확인.  
2단계(중간 난도): OpenCode에 BlockNote MCP 연결, 읽기·포스트잇 저장만 허용하여 도구 호출 검증.  
3단계(중간\~높은 난도): 필요할 때 BlockNote 내부에 서버 측 에이전트 실행기와 실행 제한·상태 표시 기능 구현.  
4단계(높은 난도): Gemini·Qwen·EXAONE 사이의 역할 분담, 의견 비교, 중복 검출, 근거 추적 실험.

EXAONE이 훌륭한 검토자인지의 판단은 동일 문서에 대한 실제 검증 품질·오류율·지연·호출 비용/한도로 확인한다.

\#\# 6. 필수 운영 안전장치  
\- 최소 권한 시작: read\_document / list\_postits / save\_postit 중심. 본문 편집·삭제 및 코드 실행은 별도 승인.

\#\# 1. OpenCode의 정체  
OpenCode는 Claude Code나 Codex CLI와 유사한 오픈소스 AI 코딩 에이전트 프로그램이다. 다양한 LLM을 연결해 코드 저장소를 분석하고, 파일 수정안을 만들고, 명령어·테스트를 실행하며, 작업을 대화로 지시할 수 있다.

EXAONE과 연결했을 때 역할:  
\- EXAONE: 코드를 이해하고 다음 조치를 판단하는 추론 모델(두뇌)  
\- OpenCode: 파일 읽기·수정, 명령어·테스트 실행, 변경 내용 비교(실행기)  
\- BlockNote MCP: 문서·포스트잇 데이터에 접근하는 통로

즉 EXAONE 자체가 파일을 직접 수정한다기보다, OpenCode가 EXAONE의 도구 호출·지시에 따라 권한 안에서 작업한다.

\#\# 2. 사용 환경과 기능  
\- 터미널 TUI, 데스크톱 앱, 웹 인터페이스 등의 작업 방식 제공(제공 범위는 버전에 따라 확인)  
\- Git 저장소를 읽고 수정 변경점(diff)을 확인  
\- 모델 교체 및 MCP 연결 지원  
\- 승인 및 실행 권한 범위를 제한할 수 있음  
\- 실제 도구 기능과 모델 호환성은 설치 환경·버전마다 검증 필요

\#\# 4. BlockNote Lab 실제 적용 예시  
OpenCode + EXAONE에게:  
"블락노트랩의 포스트잇 삽입 기능을 분석해 줘. 공개 Markdown에서 줄바꿈이 사라지는 문제의 원인을 찾아 수정안을 만들고 테스트해. 기존 기능에 영향을 줄 수 있는 수정은 승인받아."

예상 작업:

1) 프로젝트 소스 파일 분석
2) 포스트잇 삽입 및 Markdown 내보내기 경로 추적
3) 수정안 및 변경점(diff) 제시
4) 테스트 실행 및 결과 보고
5) 승인 후 통합 또는 별도 브랜치 작업

코드 오작동 가능성이 있으므로 별도 브랜치에서 검증하고 무승인 배포는 금지한다.

1. 구글 로그인이 안 되는 원인과 우회 방법

현재 BlockNote Lab 배포 사이트는 첫 화면에서 Sign in with ChatGPT 로그인 게이트를 거치도록 설정되어 있으며, 접속 환경에 따라 아래 두 가지 이유로 Google 로그인이 실패합니다.

- 원격 브라우저·인앱 WebView 차단 (가장 유력한 원인): 방금처럼 외부 탐색 도구의 원격 브라우저 창이나 모바일 인앱 브라우저(WebView) 안에서 ChatGPT로 계속 → Google로 계속을 누르면, Google이 자동화 제어 신호나 임베디드 환경을 감지해 "이 브라우저 또는 앱은 안전하지 않을 수 있습니다" 메시지와 함께 로그인을 원천 차단합니다 (Google 계정 지원 안내).

- 일반 브라우저에서도 실패하는 경우: PC나 스마트폰의 기본 Chrome·Safari에서 직접 열었는데도 안 된다면, ChatGPT Sites 권한 설정에서 공개 범위가 소유자 전용으로 닫혀 있어 다른 Google 계정이 거부되거나, 브라우저의 서드파티 쿠키 차단 때문에 [auth.openai.com](<https://auth.openai.com/>)과 .[chatgpt.site](<https://chatgpt.site/>) 사이의 인증 세션(oai-login-csrf 쿠키) 전달이 끊기는 경우입니다 (OpenAI 쿠키 정책).

- 즉시 우회하는 방법: 원격 브라우저 창에서 로그인할 때는 Google로 계속 버튼 대신 이메일 주소 직접 입력 + 이메일 인증 코드(또는 비밀번호) 방식을 선택하면 Google 보안 차단을 거치지 않고 통과할 수 있습니다. 내부 화면 UI 검토가 목적이라면 ChatGPT Sites 게시 설정을 잠시 공개 링크로 전환하거나, 현재 화면 캡처를 바로 올려주셔도 빠르게 함께 볼 수 있습니다.

1. 공유 메모리 문서(엑사원 연동 방향) 검토 결과

작성해 두신 공유 메모리 문서의 3개 파트(K-EXAONE 2.5 API 연동, 에이전트·MCP 확장, OpenCode·Hermes 비교)를 검토한 결과, 기본 아키텍처 방향은 탄탄하며 실제 구현에 들어가기 전에 아래 검증 포인트만 구분해 확인하면 시행착오를 크게 줄일 수 있습니다.

- 유지할 핵심 강점 (권한 격리 및 프록시 추상화): AI에 본문 수정 권한을 주지 않고 포스트잇 보관함(save\_postit)에만 검토 의견을 남기게 한 구조 덕분에 모델 선택지를 Gemini·Qwen·K-EXAONE 2.5로 늘려도 본문 상태 충돌 위험이 격리됩니다. 또한 OpenAI 호환 엔드포인트를 서버 측 프록시(Cloudflare Worker 등) 뒤로 통일해 프런트엔드 변경을 최소화한 접근도 합리적입니다.

- 체크포인트 1 — [chatgpt.site](<https://chatgpt.site/>) 호스팅 환경의 외부 프록시 호출 제약: 현재 개발 중인 \*.[chatgpt.site](<https://chatgpt.site/>) 런타임은 샌드박스 및 CSP(콘텐츠 보안 정책) 규칙에 따라 외부 개인 Worker 도메인으로의 직접 fetch가 제한될 수 있습니다. 모델 선택기 UI를 작업하기 전에, 현재 호스팅 환경에서 외부 프록시 엔드포인트로 단일 테스트 요청이 정상 통과하는지부터 먼저 확인해야 합니다.

- 체크포인트 2 — 일일 100회 쿼터와 에이전트 루프 호출량의 불일치: 1부 문서의 단발성 포스트잇 검토(1클릭 = 1호출)에서는 무료 일 100회 한도로 충분하지만, 2부 문서처럼 에이전트가 BlockNote MCP 도구(list\_documents → read\_document → save\_postit)를 연속 호출하면 작업 1건당 API 호출이 4\~10회 이상 발생합니다. 에이전트 단계로 넘어갈 때는 깊은 한국어 검토 호출만 K-EXAONE 2.5에 맡기고, 반복적인 도구 라우팅은 쿼터 여유가 있는 모델이나 low 추론 강도로 분리하는 구성이 현실적입니다.

- 체크포인트 3 — reasoning\_content 타임아웃 및 저장 규칙 분리: 추론 강도를 high·max로 설정하면 reasoning\_content 생성 시간이 길어져 일반 단발성 HTTP 요청에서는 프록시 타임아웃에 걸리기 쉽습니다. 프록시 구간은 SSE 스트리밍을 기본으로 고려하되, 포스트잇 카드 본문에는 최종 content만 저장하고 reasoning\_content는 접기 영역(근거 보기) 메타데이터로 분리하거나 버리는 스키마를 미리 고정해 두는 편이 깔끔합니다.

- 체크포인트 4 — 개발 에이전트(OpenCode)와 앱 내 문서 에이전트의 경계 분리: 3부에서 비교한 OpenCode는 로컬 코드 수정·테스트에 특화된 코딩 에이전트이므로 BlockNote Lab 자체의 소스 코드를 개발하는 용도로 한정하는 편이 맞습니다. 반면 앱 안에서 문서를 읽고 포스트잇을 남기는 작업은 별도 무거운 에이전트 실행기를 끼우기보다, 서버 프록시 내부의 2\~3단계 고정 Tool-calling 루프로 처리하는 편이 디버깅과 응답 속도 면에서 훨씬 유리합니다.

\#\# I. 이번 실험의 목적과 판단  
목표는 EXAONE을 BlockNote Lab에 곧바로 추가하는 것이 아니다. Galaxy Z Fold5의 Samsung DeX에서 OpenCode + K-EXAONE을 독립 실행하고, 실제 에이전트로 쓸 만한지 검증한 다음 BlockNote MCP 연결 여부를 결정한다.

이 순서가 좋은 이유:  
\- 기존 BlockNote Lab, Gemini/Qwen 설정, 현재 문서/포스트잇 운영을 보호한다.  
\- OpenCode 설치 환경 문제와 EXAONE API의 모델·도구 호출 문제를 구분할 수 있다.  
\- 실패해도 환경과 설정을 되돌릴 수 있게 한다.  
\- 같은 모델이라도 OpenCode 실행기와 MCP 도구를 통해 활용 범위를 넓힐 수 있다.  
\- 문서의 소유자와 최종 승인자는 사용자이며, AI의 검토는 우선 포스트잇에 남긴다.

\#\# II. Carbon의 개발 담당 범위  
Carbon이 책임질 것:

1. Fold5 Android/ARM64, DeX, Termux 환경의 OpenCode 공식 지원·호환성 조사.
2. 기존 Termux 내 Claude MCP 서버와 충돌하지 않는 독립 실행 구조 선정(별도 설정·폴더·프로세스·포트·의존성).
3. OpenCode 실행 환경 구축 또는 기기 직접 조작 권한이 없을 경우 정확한 설치 명령과 사용자의 실측 검증 절차 제시.
4. EXAONE API를 단독 모델로 연결하고 한국어 응답/도구 호출/에러 처리를 검증.
5. DeX 키보드·마우스·브라우저/TUI 사용성, 재접속·종료·재기동·복구 절차 작성.
6. EXAONE 호출 횟수·지연·실패·사용량 기록, 최종 결과 증거 및 인계서 정리.
7. 이후 BlockNote MCP 연결 가능성·인증·최소 권한·CSP/프록시 제약 조사(구현은 다음 단계).

Carbon이 아직 담당하지 않을 것:  
\- 기존 BlockNote Lab 코드 수정·모델 버튼 추가·프로덕션 배포  
\- 실제 BlockNote MCP 연결 및 문서·포스트잇 쓰기  
\- 기존 Claude MCP 서버 종료/교체/환경 수정  
\- Google 로그인 보안 우회 또는 블락노트 사이트의 공개 범위 변경  
\- 다른 유료 LLM으로 자동 폴백, 무제한 자동 실행

Carbon에게 단말/서버 조작 권한이 없는 상태라면 ‘실행 완료’가 아닌 ‘설치 안내 완료’와 ‘사용자가 확인해야 할 항목’을 명확히 분리한다.

\#\# III. 실험 단계와 통과 기준

\#\#\# 0단계 — 현황 실사 / 위험 평가  
\- 설치 전에 OS·아키텍처·Termux 패키지·Node 버전·현재 서버/포트/프로세스·기존 설정 보호 대상을 읽기 전용으로 조사한다.  
\- ‘전용 폴더’만으로 완전 격리되는 것은 아니다. 전역 npm 패키지, PATH, 셸 설정, 실행 프로세스, 포트까지 고려한다.  
통과: 기존 서버를 건드리지 않는 설치/복구 계획이 확보됨.  
보류: 기존 파일 또는 서버 변경 없이는 진행이 어렵다면 승인 전 멈춤.

\#\#\# 1단계 — OpenCode 자체 기동  
\- 공식 OpenCode 설치 자료의 현재 패키지명과 ARM64/Android 지원 여부 확인.  
\- 가능하면 독립 Termux 실행을 검증하고, 불가능하면 proot Linux 또는 별도 Linux/PC OpenCode에 Fold5 브라우저로 접속하는 대안을 비교한다.  
\- 비공식 바이너리·임의 스크립트는 출처/위험을 설명하고 승인 후에만 실행.  
통과: 기존 서버에 영향 없이 버전 확인, 시작, 종료, 재시작 성공.

\#\#\# 2단계 — EXAONE 단독 API 연동  
\- 공식 안내의 Base URL, 실제 모델 ID, API 키, OpenAI 호환 엔드포인트 및 tool calling 지원 확인.  
\- EXAONE만 선택하여 간단한 한국어 요청을 보낸다. 인증 실패·쿼터·타임아웃·응답 포맷 오류도 점검한다.  
\- 키와 토큰을 로그·채팅·소스·스크린샷에 노출하지 않는다.  
통과: 실제 EXAONE 모델 응답 확인, 별도 유료 모델 호출 없음.

\#\#\# 3단계 — 코딩 에이전트 도구 실행  
\- 독립 테스트 디렉터리에서 파일 읽기, 간단한 소스 작성/수정, 테스트 명령 실행, diff 확인까지 검증.  
\- EXAONE의 도구 호출 판단 → OpenCode 실행 → 결과 재입력 → 최종 응답을 각각 관찰.  
통과: 최소 한 사이클이 실제로 성공하고 작업 범위 밖 파일 변경 없음.  
실패 시: 실행기 문제인지 모델 tool-call 형식 문제인지 구분해 보고.

\#\#\# 4단계 — DeX 사용성·안정성  
\- 키보드·마우스, 화면 배치, 터미널/웹 UI 중 실제 사용 경로, 재접속, 종료/재실행 테스트.  
\- 웹 UI를 사용한다면 처음에는 localhost(127.0.0.1)로 제한; 외부 IP 바인딩 또는 포트 공개는 별도 승인.  
\- 기존 Claude MCP 서버가 작업 전후 정상 동작하는지 비교.  
통과: 사용자가 Fold5에서 혼자 켜고, 쓰고, 종료하고, 복구할 수 있음.

\#\#\# 5단계 — BlockNote MCP 활용성 조사(이번에는 설계만)  
\- MCP 클라이언트 연결 가능성, URL/인증 헤더, 도구 스키마, 외부 연결 제약을 조사한다.  
\- 우선 후보 도구: list\_documents, read\_document, list\_postits, read\_postit, save\_postit.  
\- insert\_postit, apply\_paragraph\_edits처럼 본문을 바꾸는 도구는 후속 승인 전 제외한다.  
\- 초기 실험 시나리오 설계: ‘엑사원 연동 방향’ 문서 읽기 → 기존 코멘트 중복 확인 → 새 검토 의견을 포스트잇 보관함에 저장.  
통과: 연결 조건·권한·보안 위험과 최소 실험 절차가 문서화됨. 실제 연결과 저장은 사용자 별도 승인 후 수행.

\#\# IV. Carbon의 추가 검토에 대한 합의  
\- GPT Site의 Google 로그인 문제는 원격 브라우저/OAuth 제한 가능성이 있지만 원인이 확정된 것은 아님. OpenCode 독립 구축의 선결 조건으로 취급하지 않음.  
\- BlockNote 호스팅 환경에서 외부 프록시 fetch/CSP 제한이 있을 수 있음. 실제 BlockNote 통합 단계에서 테스트; 현재는 가정으로 확정하지 않음.  
\- EXAONE 무료 API 호출 한도와 키 유효기간/비상업적 이용 약관은 발급 시점 공식 문서로 검증. Carbon이 제안한 에이전트 작업당 4\~10회 요청은 추정이므로 실측 기록 우선.  
\- reasoning\_content와 최종 content를 구별하고, 내부 추론 원문을 문서나 포스트잇에 무분별하게 보존하지 않음. 스트리밍 도입도 실제 지연·타임아웃 결과를 보고 판단.  
\- OpenCode는 우선 개발 에이전트로 실험하지만 BlockNote MCP를 통한 문서 에이전트 사용 가능성도 열어둠. 앱 내부에서 별도 문서 에이전트 실행기를 구현할지는 후속 결정.  
\- 기존 BlockNote의 서버 중심·포스트잇 보관함/임시 답변 격리·사용자 승인 원칙을 그대로 유지한다.

\#\# V. 보안/권한/중단 기준  
절대 무단 변경 금지: 기존 Claude MCP 서버·Termux 전역 설정·기존 BlockNote 코드·배포·문서 본문·공개 설정·인증 정보.  
사전 승인 필요: 비공식 바이너리 실행, 전역 설치·업데이트, 기존 서비스 프로세스/포트 변경, 외부 네트워크 노출, 실제 BlockNote MCP 연결, 기존 프로젝트 파일 수정.  
호출 제한: 반복 횟수/호출 횟수/시간/실패 재시도 상한을 두고, 무한 루프를 방지한다.  
중단 신호: 기존 서버 불안정, 키 노출 위험, 약관 제약, 에이전트의 작업 경계 이탈, 연속 호출 실패, 자격 증명 누출 우려.

\#\# VI. 최종 인수 자료와 다음 결정  
Carbon의 납품 항목: 설치 경로·버전·실행 방법·종료 방법·복구/제거 방법·실제 검증 증거·EXAONE 호출 현황·DeX 사용성·기존 서버 충돌 여부·MCP 연결 사전 검토.

폴드3의 기존 인프라와 물리적으로 완전히 분리된 새 기기라면, 폴드5 DeX 환경은 **독립 에이전트 실험·검증용 워크스테이션으로 충분히 적합합니다.** 다만 순정 리눅스 PC처럼 설치 한 줄로 끝나는 환경은 아니므로, 아래 네 가지 기준에서 **조건부 적합**으로 판단하시는 것이 정확합니다.

- **Android 세션 유지 제약 (초기 설정 필수)**: EXAONE이 긴 추론(` reasoning_content `)을 수행하는 수십 초 동안 Android의 백그라운드 프로세스 제한(` signal 9 `)이 터미널 세션을 끊을 수 있으므로, 폴드5 **개발자 옵션의 하위 프로세스 제한 해제**와 Termux 배터리 최적화 예외 설정은 처음부터 켜 두어야 안정적입니다 ([OpenCode Android 실행 경로 비교](<https://cosyra.com/guides/opencode-on-android.html>)).

\# 공유 메모리 설계 원칙: 기억은 각자의 것, 문서는 서로에게 건네는 것

작성: ChatGPT · 2026-11-13  
배경: BlockNote Library Site(ChatGPT·Gemini), 폴드5의 OpenCode + EXAONE 독립 실험실, 로컬 BlockNote 간 공유 메모리 구조를 검토하는 과정에서 도출한 설계 방향.  
상태: 설계 합의에 가까운 방향. 자동 동기화나 신규 저장소 구현을 승인한 것은 아님.

\#\# 1. 핵심 판단  
AI마다 가진 메모리, 대화 기록, 작업 로그, 포스트잇까지 하나로 통합하지 않는다. 각 AI와 환경은 자신만의 기억과 작업 공간을 유지한다. 상호 소통이 필요할 때는 사용자가 선택·정리한 '문서 본문 한 장'만 공유한다.

표현: \*\*기억은 각자의 것, 문서는 서로에게 건네는 것.\*\*

이렇게 하면 서로의 기억을 침범하지 않으면서도 같은 문서를 공통 맥락으로 읽고 독립적으로 판단할 수 있다. 문서는 AI 메모리 복제본이 아니라, 사용자에 의해 편집되고 승인된 '맥락 문서(context artifact)'다.

\#\# 2. 각 요소의 역할  
\- 개별 AI 메모리·대화·실행 로그: 해당 모델/서비스/기기에만 남는 독립적인 내부 맥락. 기본적으로 공유하지 않음.  
\- 포스트잇: 각 환경에서 생성한 제안, 반론, 검토 기록. 해당 환경에서만 보관하고 다른 환경과 동기화하지 않음.  
\- 문서 본문: 사용자가 여러 자료·포스트잇에서 필요한 내용만 선택해 배치한 공유 대상. 판단 근거, 현재 입장, 미확인 가설, 열린 질문을 필요에 따라 포함.  
\- 문서 불러오기: 다른 AI가 자신의 기존 메모리를 유지한 채 같은 문서 본문을 추가 맥락으로 받아들이는 행위.  
\- 본문 삽입: 해당 의견을 다른 AI와 공유할 만큼 가치 있다고 사용자가 선택하는 승인 절차.

\#\# 3. 작업 흐름  
A. Library Site 또는 로컬 BlockNote에서 사용자가 문서를 작성·편집한다.  
B. GPT·Gemini·EXAONE 등은 각자 문서를 검토하고, 의견을 자기 환경의 포스트잇/로컬 기록에 보관한다.  
C. 사용자는 공유하고 싶은 내용만 자기 문서 본문에 삽입하여 맥락을 재구성한다.  
D. 공유 문서의 승인된 본문만 Markdown 등 읽기 가능한 형태로 전달한다.  
E. 다른 모델은 이를 읽고 자신만의 해석·작업을 이어간다. 각자의 기존 메모리와 포스트잇을 이 과정에서 통합하지 않는다.

예: Library Site의 '엑사원 연동 방향' 본문을 폴드5 OpenCode+EXAONE이 읽는다. EXAONE의 도구 실행 결과·검토 기록은 폴드5에 남기고, 가치 있는 결론만 사용자가 문서에 다시 반영한다.

\#\# 4. 이 구조를 선택한 이유  
\- 메모리·포스트잇 전체 동기화가 만드는 충돌, 최신성, 보안, 권한 관리 문제를 피할 수 있다.  
\- 여러 AI가 동일한 자료를 보되 서로의 판단에 무조건 동조하지 않고 독립적인 견해를 유지할 수 있다.  
\- 새로운 무료/유료 모델이나 실행 환경이 생겨도 문서만 불러오면 참여 가능하다.  
\- '무수한 정보 중 무엇을 한 문서에 남길 것인가'라는 핵심 편집 행위를 사용자에게 남긴다.  
\- 모델이나 서비스가 종료돼도 승인된 문서를 재사용할 수 있다.

\#\# 5. 초기 기술 설계  
\- 공유 범위: 문서 본문과 식별에 필요한 최소 정보(제목, 문서 ID, 버전/발행 시각).  
\- 비공유 범위: 각 환경의 포스트잇, 임시 답변, 개인 메모리, 실행 로그, 인증 정보.  
\- 1차 실험: 기존 공개 Markdown 발행 방식 등을 이용해 승인된 문서 한 장을 폴드5에서 읽기 전용으로 가져온다. 공개 GitHub에는 공개 승인된 내용만 올린다.  
\- 자동 양방향 동기화, 단일 공통 DB, 포스트잇 통합은 당장 만들지 않는다.  
\- 내용이 갱신될 때는 출처와 버전을 표시하고, 과거 버전 또는 마지막 정상 사본을 보존하는 방식을 검토한다.  
\- 문서 전체를 실시간으로 합칠 필요가 없다. 환경별 편집본이 달라도 특정 시점의 본문을 명시적으로 건네는 방식이 가능하다.

\#\# 6. 유의할 점과 열려 있는 질문  
\- 문서를 공유하면 상대 AI의 영구 메모리를 수정하는 것은 아니지만, 읽은 내용은 그 AI의 현재 판단에 의도적으로 영향을 준다. 따라서 사실·가설·결정·미해결 질문을 구분해 담는 것이 좋다.  
\- 본문만 공유하면 포스트잇에만 있는 변경 이유를 다른 AI가 모를 수 있다. 공유할 가치가 있는 판단 근거는 본문에 함께 편집한다.  
\- 문서 공개 범위(공개 URL과 인증된 비공개 접근), 버전 충돌 시 처리, 변경된 내용을 로컬에서 Site로 돌려보내는 절차는 실제 사용 후 결정한다.  
\- 로컬 실행 환경과 Library Site의 완전 통합은 지금 단계에서 불필요하고 위험 요소가 많다.

\#\# 7. 다음 최소 실험

1) 사용자가 문서 한 장에 필요한 맥락만 삽입해 승인한다.
2) 그 본문을 읽기 전용 Markdown/파일로 폴드5 OpenCode+EXAONE이 불러온다.
3) EXAONE이 문서를 읽고 검토 작업을 수행한다.
4) 결과와 포스트잇은 EXAONE 측에 독립 저장한다.
5) 필요할 때 사용자가 결과 중 일부만 공유 문서 본문에 다시 반영한다.

결론: 공유 메모리의 본체는 거대한 동기화 시스템이 아니라, 사람이 선택하여 편집한 문서 한 장이다. 블락노트의 포스트잇·삽입·편집 기능 자체가 공유할 맥락을 선별하는 과정이며, AI는 그 문서를 매개로 협력하는 일시적 참여자다.

상태: 구현 지시가 아닌 설계 변경 제안. Carbon의 검토 및 소스 실사 후 개발 범위를 확정한다.

\#\# 1. 배경과 판단의 변화  
당초 Fold5 DeX에 Termux + Ubuntu(proot) + OpenCode + EXAONE을 설치해 독립 에이전트로 시험하려 했으나, 사용자는 OpenCode와 외부 서비스의 커넥터·런타임 운영 부담이 예상보다 클 수 있다고 판단했다. 기존 Chat AI v0.3.2의 채팅 인터페이스를 재활용해 EXAONE 전용 웹 작업실로 개조하고, 필요하다면 GPT까지 함께 사용하는 방안을 우선 검토한다.

핵심 질문: ‘우리에게 필요한 것이 완성형 코딩 에이전트(OpenCode)인가, 아니면 안정적인 채팅 UI에 소수의 검증된 도구를 붙인 웹 에이전트인가?’

목표는 기존 BlockNote Lab이나 Claude 앱을 대체하는 것이 아니다.  
\- Claude는 기존 Claude 앱·폴드3의 MCP 환경에서 독립적으로 사용한다.  
\- 폴드5 DeX에는 Chat AI 기반 EXAONE·GPT 웹 채팅/작업 환경을 후보로 둔다.  
\- BlockNote Library Site는 승인된 맥락 문서의 편집·전달 공간으로 유지한다.  
\- AI별 메모리·포스트잇·채팅 이력은 독립적으로 관리하고, 필요할 때 문서 본문 한 장만 공유한다.

\#\# 2. 제안 아키텍처  
Galaxy Fold5 DeX 브라우저  
→ Chat AI 기반 독립 Web UI (EXAONE 채팅 / GPT 채팅; 독립 세션)  
→ 인증·모델 호출·도구 승인·로그를 처리하는 서버 계층  
→ EXAONE API 및 지원되는 GPT 연결 방식  
→ 필요한 경우에만 제한된 도구 실행기 (문서 불러오기, 파일 읽기, 검토 결과 로컬 저장 등)

원칙:  
\- Chat AI의 UI를 복사·분기하여 시험한다. 원본의 Claude/병렬 모델 기능과 기존 BlockNote Lab 배포에는 영향 주지 않는다.  
\- EXAONE은 처음에 ‘API 기반 채팅’으로 연결한다. 파일/웹/명령 도구 실행은 단계적으로 추가한다.  
\- GPT 연결은 기존 Chat AI에 어떤 공식 지원 방식이 있는지 실제 소스를 먼저 확인한다. OpenAI API 키(별도 과금)와 ChatGPT 로그인 기반 접근은 권한·지원 범위가 다르므로 동일하다고 가정하지 않는다. 공식적으로 허용·지원되는 방법만 적용한다.  
\- OpenCode 수준의 범용 권한, 무제한 도구 호출, 클라우드 컴퓨터 기능을 초기부터 목표로 하지 않는다.

\#\# 3. Carbon에게 요청하는 첫 번째 작업: ‘개발 전 검토’

1) 기존 Chat AI v0.3.2 소스와 현재 실행 경로, UI 구성, 모델 호출/병렬 처리, 사용자 세션, 토큰 관리, 저장 방식, 도구 관련 코드 조사.
2) Chat AI를 독립 복사본으로 구성해 EXAONE + GPT 두 모델의 채팅 환경으로 전환할 수 있는지 확인.
3) EXAONE 공식 문서 기준 API 엔드포인트·모델 ID·인증·응답 형식(content 등)·tool calling·스트리밍·무료 사용/이용약관 검증.
4) GPT 연결은 현재 소스의 실제 로그인 방식이 공식적으로 사용 가능한지 확인하고, 불가하면 별도 OpenAI API 경로와 비용을 명시.
5) Fold5 DeX에서 동작시킬 최저복잡도 배포 방식(기존 웹 서버 재사용, 별도 가벼운 로컬 서버, 로컬 전용 웹 UI 등) 비교. 별도 Ubuntu/proot가 정말 불필요한지 판단.
6) 독립 Chat AI 시험실을 만들 때 원본과 공유할 코드·독립 분리할 데이터·설정·포트·인증·비밀값의 경계 정의.
7) 최소한의 에이전트 실행기 설계(허용 도구 목록, 호출 횟수/시간 상한, 사용자 승인 단계, 실패·롤백, 결과 기록) 제안.
8) OpenCode와 비교해 개발량, 유지보수, 안정성, 도구 생태계, Fold5 사용성의 장단점 보고.
9) 단계별 실험에 대한 구현 가능/제약/불명확한 사안을 구분하고, 기존 코드를 변경하기 전 검토 보고.

\#\# 4. 제안 실험 순서와 성공 조건  
A. 독립 UI 재사용: Chat AI 원본을 변경하지 않는 복사본에서 채팅 인터페이스와 세션이 실행되는지 확인.  
B. EXAONE 단독 채팅: 한국어 멀티턴, 스트리밍(지원 시), 응답 보관, 오류 표시, 호출 안정성 확인.  
C. 최소 도구 실행: 테스트용 파일 읽기 → 검토 요청 → 결과 파일 저장의 ‘한 사이클’을 사용자 승인 하에 실행. 명령 실행/파일 수정은 후속 실험.  
D. GPT 연결 가능성 검토 및 독립 채팅 구성: EXAONE과 메모리·이력 자동 혼합 금지. 공식 인증 방법과 비용/약관 확인 후 실행.  
E. 공유 문서 불러오기: BlockNote Site가 발행한 ‘승인된 문서 본문’만 읽기 전용으로 가져오기. 포스트잇/개인 메모리/작업 로그 동기화는 하지 않음.  
F. 실사용성 비교: 응답 시간·API 호출 성공률·도구 실행 성공률·재접속·DeX 입력·유지보수 부담을 OpenCode 경로와 비교하여 계속 개발할지 판단.

\#\# 5. 하지 않을 것 / 보존할 것  
\- 원본 Chat AI, 기존 BlockNote Lab, 기존 Gemini/Qwen 연결, 폴드3 Claude MCP 서버를 무단 변경하지 않는다.  
\- BlockNote 문서 본문을 외부 AI가 자동 수정·배포하지 않는다.  
\- 현재 라이브러리 사이트와 로컬 BlockNote의 데이터베이스·포스트잇·AI 메모리를 합치지 않는다.  
\- 앱의 공개 접근 권한을 낮추거나 인증을 우회하지 않는다.  
\- API 키/액세스 토큰을 브라우저 JS·공개 GitHub·작업 로그에 노출하지 않는다.  
\- 새 기능을 위해 복잡한 다중 커넥터 생태계나 자동 동기화를 선행 개발하지 않는다.

\#\# 6. 열린 설계 질문  
\- 실제 Chat AI v0.3.2가 현재 얼마나 독립적인지? 어디까지 UI만 재활용 가능한지?  
\- GPT 연결은 기존에 사용하던 공식 지원 인증 흐름을 재사용할 수 있는지, 아니면 별도 API 비용이 필요한지?  
\- EXAONE 무료 API의 제3자 서비스 제공 제한과 개인 비상업적 시험 범위는 무엇인지?  
\- 작은 자체 도구 실행기가 OpenCode보다 유지보수 측면에서 정말 유리한지? (초기 개발비와 장기 운영비 구분)  
\- 접속 환경은 폴드5에서 직접 구동하는 로컬 서버가 나은지, 인증된 원격 사이트가 나은지?  
\- 웹 UI의 에이전트 도구를 어느 단계까지 허용하는 것이 안전한지?

\#\# 7. 권장 결론  
Carbon은 우선 OpenCode 설치 작업을 보류하고 기존 Chat AI의 소스·런타임 구조를 조사하여 ‘EXAONE 전용 채팅 웹 UI + 최소 도구 실행기’가 더 가벼운 대안인지 비교하자. EXAONE API 채팅 성공을 가장 작은 1차 목표로 삼고, GPT와 에이전트 기능은 독립적인 후속 단계로 다룬다.  
‘기억은 각자의 것, 문서는 서로에게 건네는 것’이라는 공유 컨텍스트 원칙을 유지한다.
